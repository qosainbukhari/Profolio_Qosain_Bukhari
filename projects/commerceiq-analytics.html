CommerceIQ Analytics Platform

A full-stack analytics platform that turns raw e-commerce transactions into an interactive business-intelligence dashboard. CSV files are cleaned and loaded into a relational MySQL database with Pandas; 13 SQL queries compute KPIs, revenue trends, growth and rankings; FastAPI serves them; and a React dashboard shows them as charts and tables.

01The problem

Raw transaction exports don't answer anything on their own. A business wants to see revenue over time, its best products and sellers, where its customers are and how they pay, in one place and straight from the database rather than in one-off spreadsheets.

02Data

The Olist Brazilian E-Commerce public dataset: about 100K orders from 2016 to 2018, split across linked tables for customers, orders, order items, products, sellers, payments and reviews. That structure makes it a realistic exercise in relational modelling and JOIN-heavy SQL.

03Approach

  1. Model the data relationally. Seven MySQL tables (customers, orders, order_items, products, sellers, payments, reviews) linked by order, customer, product and seller IDs.
  2. Load it with a Pandas ETL. A reusable loader reads each CSV, keeps the needed columns and writes it to MySQL through SQLAlchemy and PyMySQL, with credentials read from .env.
  3. Answer business questions in SQL. Thirteen query files, kept separate from the Python code: JOINs across orders, payments, order items, products and sellers, with GROUP BY aggregations for revenue, top products, top sellers, customer states, payment types and order status.
  4. Measure growth over time. A CTE builds monthly revenue, and a LAG() window function compares each month with the previous one to compute month-over-month growth.
  5. Serve the results. A FastAPI backend runs each query and exposes it as one of 12 GET endpoints, covered by 10 Pytest endpoint tests.
  6. Build the dashboard. React, Tailwind CSS and Recharts across 7 pages, with KPI cards, charts, tables and a year filter; Docker Compose runs MySQL, the backend and the frontend together.

The month-over-month growth query, from backend/queries/monthly_growth.sql:

WITH monthly_revenue AS (
    SELECT DATE_FORMAT(o.order_purchase_timestamp, '%Y-%m') AS `year_month`,
           SUM(p.payment_value) AS revenue
    FROM orders o
    INNER JOIN payments p ON o.order_id = p.order_id
    GROUP BY `year_month`
),
growth_data AS (
    SELECT `year_month`, revenue,
           LAG(revenue) OVER (ORDER BY `year_month`) AS previous_month_revenue
    FROM monthly_revenue
)
SELECT * FROM growth_data;

Reading the numbers carefully. Building the dashboard surfaced three data issues that would mislead a business user: customer counts that are really order counts, two near-empty months at the end of the data, and reais shown as dollars. They are listed under limitations as the next fixes.

06Limitations

  • Olist gives each order its own customer_id, so “total customers” equals total orders (99,441); counting customer_unique_id would give the real number of distinct customers.
  • The dataset ends in late 2018, so September and October 2018 show almost no revenue; the chart should stop at the last complete month.
  • Payment values are in Brazilian reais, but the dashboard labels them with “$”.
  • No authentication, caching or forecasting yet; Redis caching and a revenue forecast are the planned next steps.
