Document Q&A RAG Chatbot

Upload a PDF and ask questions; answers come only from the document, with page citations and per-session chat memory. The project started as a naive RAG pipeline and was upgraded to advanced RAG: parent-child chunking, hybrid BM25 + dense search, cross-encoder reranking, contextual compression and query rewriting. Every technique can be switched on or off, and an evaluation measures whether it actually helps.

01The problem

Long PDFs such as lecture notes, papers and textbooks are slow to search, and a plain LLM answers confidently without saying where its answer came from. Answers need to come from the document and show the page so the reader can check them.

Advanced RAG techniques are often added because they sound better. I wanted to know whether each one actually helps on a given document, so every technique is a config switch with an evaluation behind it.

02Data

An evaluation set of 25 questions about a 15-page ML lecture deck (samples/Ml_book.pdf), each with a reference answer and the page or pages that contain it. The PDF is indexed into a temporary folder for each run, so the real database is never touched.

03Approach

  1. Chunk for search and for context. Parent-child chunking: 300-character children are searched, and their 1,500-character parents are sent to the LLM. Stable chunk IDs mean re-uploading a file replaces it instead of duplicating it.
  2. Search two ways. Dense MiniLM embeddings in ChromaDB plus a BM25 keyword index, fused with Reciprocal Rank Fusion.
  3. Rerank and compress. A cross-encoder re-scores about 20 candidates down to the top 4, and compression keeps only the sentences relevant to the question, with page metadata intact.
  4. Handle conversations. Follow-up questions are rewritten into standalone ones using the session's history. Multi-query, HyDE and query decomposition are available as switches.
  5. Measure every switch. Recall@1/2/4 and MRR are computed in plain Python from page numbers. Faithfulness, context precision and context recall use LLM-as-judge prompts that only give yes/no verdicts; Python computes the scores.
  6. Ship and observe. FastAPI backend, Streamlit chat UI and Docker Compose, with optional Langfuse tracing that records every step as a span with its latency.

On this document the simplest pipeline won. It is a small deck where almost every page says “machine learning”, so BM25's keyword ranking is noisy, and the cross-encoder, trained on web search passages, sometimes preferred a general page over the specific slide. Advanced techniques are built for large, varied corpora; the evaluation is there so they can be tested on real documents before being switched on.

Answer quality (LLM-as-judge, openai/gpt-oss-20b): faithfulness 0.952 and context recall 0.984 for the naive pipeline, 0.927 and 0.984 with hybrid search.

Replacing my own claim. The first version of this project reported 85% retrieval accuracy and 90% faithfulness from a quick hand check. I built a proper evaluation and replaced those numbers with measured ones, including the results that show the fancier techniques didn't help here.

06Limitations

  • The evaluation uses one small document; a larger, more varied set is needed to tune top_k and the thresholds.
  • Context precision is low (0.33–0.37) because 4 chunks are always sent while most answers sit on one page.
  • Sessions live in memory and parent chunks in a JSON docstore; Redis and a database would be the next step.
  • No answer streaming or authentication yet, and the free Groq tier allows about one full judged run per model per day.
